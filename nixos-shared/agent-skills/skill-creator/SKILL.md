# Skill Creator (local)

Local conventions for writing and installing skills on this machine. The eval
pipeline lives upstream and is not duplicated here.

## Which skill for what

| Task | Use |
|---|---|
| Write, review or restructure a skill; install it via nixos-config | this skill |
| Run test cases with-skill vs baseline, grade, benchmark (pass rate, time, tokens), eval viewer, blind comparison | `anthropic-skills:skill-creator` |
| Optimise the `description` for triggering accuracy (`run_loop.py`) | `anthropic-skills:skill-creator` |

The upstream scripts call `claude -p` with the session's auth, so no
`ANTHROPIC_API_KEY` is needed. Its "package a .skill file" step does not apply
here: install as below instead.

## Install path (nixos-config)

Skills are not packaged as `.skill` zips or copied into `~/.claude/skills/` by
hand; its entries are symlinks generated by home-manager.

1. Create `~/repos/nixos-config/nixos-shared/agent-skills/<name>/SKILL.md`
   (plus `scripts/`, `references/`, `assets/` as needed). Write it by hand;
   don't create placeholder files.
2. Registration is automatic: `default.nix` turns every subdirectory holding a
   `SKILL.md` into a skill for both harnesses (claude and pi). Only skills
   sourced from flake inputs, or restricted to one harness, need an entry in
   its `webSkills`.
3. `git add` the new files. The flake `src` is the git index, so untracked
   files are invisible to `nix build`.
4. `cd ~/repos/nixos-config && nix build --no-link .#agentSkills.<name>`. The
   build fails on missing frontmatter `name`/`description`, `shellcheck
   --severity=error` findings, or Python that does not compile.
5. Rebuild the system; the skill appears in `~/.claude/skills/`.

For extra checks (reserved words, first/second-person descriptions, vague
descriptions), run `./scripts/quick_validate.py <skill-dir>`.

## Frontmatter rules

- **name**: max 64 chars, lowercase/digits/hyphens, no leading, trailing or
  double hyphens, no reserved words ("anthropic", "claude"). Gerund form
  preferred (`processing-pdfs`).
- **description**: max 1024 chars, **third person only**, no XML/angle
  brackets. It is the only trigger mechanism: say what the skill does AND when
  to use it, with the phrases users actually type. Double-quote it if it
  contains colons.
- **Err broad.** Loading a skill and not using it costs a few tokens. Missing
  it and re-solving a solved problem ruins the session.

```yaml
description: "Extracts text and tables from PDF files, fills forms, merges documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction."
```

## The three-part test

Claude is already very smart. Keep a line only if at least one holds:

1. **Outside training data**: learned through research, experimentation, experience.
2. **Context-specific**: known now, gone after the context clears.
3. **Aligns future Claude with current Claude**: behavioural guidance for consistency.

Otherwise delete it. Context with no external signal hurts performance.
Experiment with the domain before writing (try the CLIs, see what breaks);
skills built on speculation are worse than none.

## Context, attention and compaction

- An invoked SKILL.md enters the conversation as one message and **stays in
  context** for the session; it is not re-read. Every line is a recurring cost.
- Staying in context does not mean being followed. Over a long session other
  approaches win over SKILL.md prose. When a rule stops influencing behaviour,
  assume it is present but outcompeted: subtract competing lines before adding
  emphasis, sharpen the description, or move the rule into a script or hook
  where it is deterministic.
- **Compaction keeps only the head.** After auto-compaction the most recent
  invocation of each skill is re-attached, keeping its first 5,000 tokens,
  within a 25,000-token budget across all skills (most recently invoked first;
  older skills can be dropped entirely). Put load-bearing instructions early.
- This is why scripts beat prose for long sessions: a script's interface
  (`--help`, argument names, error messages) can be rediscovered by tool use at
  any time. Invest in clear `--help` output and descriptive flags.
- Write standing instructions, not one-time steps: the body persists all
  session, so "first, do X" reads as spent once X is done.

## Structure and progressive disclosure

```
skill-name/
├── SKILL.md        frontmatter + body; under 500 lines, aim far lower
├── scripts/        executable code, run without loading into context
├── references/     docs read on demand
└── assets/         files used in output (templates, images)
```

- Three loading levels: metadata (always), SKILL.md body (on trigger),
  bundled files (on demand).
- Keep references **one level deep** from SKILL.md (A→B→C leads to partial reads).
- Link with markdown syntax `[references/x.md](references/x.md)`, and say when
  to read each file. Files over 100 lines get a table of contents; for files
  over 10k words, give grep patterns in SKILL.md.
- Content lives in SKILL.md or a reference, never both.
- No README, CHANGELOG or install guides inside the skill: skills are for agents.
- Wrapping a public library or API: link its official docs.

See [references/progressive-disclosure.md](references/progressive-disclosure.md)
for splitting patterns.

## Scripts

- **Solve, don't punt**: handle errors explicitly instead of failing and leaving
  Claude to work it out.
- Single-touch commands that fold setup and teardown in; clean composable
  primitives; target workflows specific to this setup (generic tools exist).
- Nix shebangs, so no dependency installation step.
- **Paths**: the agent's cwd is the user's project, never the skill directory.
  Document scripts as `./scripts/name [args]` relative to SKILL.md, and end
  SKILL.md with:

```markdown
**Script Execution:** Always invoke scripts by absolute path: resolve
`./scripts/` against this SKILL.md's directory. All scripts use Nix shebangs,
so no dependency installation is needed.
```

## Degrees of freedom

Match specificity to fragility: text instructions where many approaches are
valid, parameterised scripts where a preferred pattern exists, fixed scripts
where the exact sequence matters.

## Testing and iterating

- Start with a single hard task; iterate until Claude succeeds, then extract the
  winning approach.
- Claude A / Claude B: one instance authors, a fresh instance runs real tasks
  with the skill. Bring the tester's concrete failures back to the author.
- Watch navigation: files read in odd order (structure unclear), references
  missed (links not prominent), the same file re-read (move it into SKILL.md),
  files never opened (cut them or signal them better).
- Ask "When would you use the X skill?" to hear the description quoted back.
- **Objectively verifiable skills** (transforms, extraction, fixed workflows):
  use the upstream eval pipeline, at least 3 scenarios, across Haiku, Sonnet
  and Opus. **Subjective skills** (writing style, design) are exempt: direct
  user feedback is the test.

Undertriggering: add the trigger phrases and technical terms users say.
Overtriggering: add negative triggers ("Do NOT use for ...") and narrow scope.
